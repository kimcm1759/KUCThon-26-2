# 음원 수집 및 정리 규칙

> Claude Code 프로젝트에 넣어 두고, 음원 파일과 자연어 설명을 전달할 때 기준 문서로 사용합니다.

> **이 프로젝트 적용 메모 (2026-11-06, 우선 적용)**
> 이 프로젝트는 출시용이 아니므로 음원 출처·라이선스를 추적하지 않는다. 아래 본문의 출처·라이선스 관련 규칙(2장 출처 설명, 8장 4번 라이선스 기록, 12장, 11장 5번 출시 빌드 제외)은 적용하지 않는다.
> - 출처·라이선스를 사용자에게 묻거나 요청하지 않는다.
> - 카탈로그 필드는 스키마 호환을 위해 유지하되 `source_url`/`source_name`/`creator`/`attribution_required`는 `null`, `license`는 `"not_tracked"`, `license_status`는 `"unverified"`로 둔다.
> - `app_use_status`는 기본 `approved`로 둔다. 파일이 없거나 설명상 해당 역할에 맞지 않을 때만 `review_required`/`not_approved`를 쓴다.
> - 준비 현황에서 `needs_review`는 라이선스가 아니라 태그 불확실·적합성 문제에만 쓴다.
> - `sounds/attributions.md`는 만들지 않는다.

## 1. 목적

사용자는 직접 음원을 수집하고, 그 음원이 어떤 물건·재질·동작에서 나는 소리인지 자연어로 설명한다. Claude Code는 이 설명과 실제로 제공된 음원 파일을 바탕으로 파일을 정리하고, 앱과 향후 사운드 추천 로직이 활용할 수 있는 메타데이터를 작성한다.

이 문서는 **음원 카탈로그를 일관된 데이터로 만드는 방법**을 정의한다. 별도 머신러닝 모델을 자동 학습시키는 규칙은 아니다. 초기 버전에서는 구조화된 카탈로그와 규칙 기반 조합을 사용하고, 충분한 데이터와 평가가 모이면 학습용 데이터로 확장한다.

## 2. 역할 분담

### 사용자가 맡는 일

- 음원 파일을 제공하거나 접근 가능한 파일 경로를 알려준다.
- 자연어로 다음 정보를 가능한 만큼 설명한다.
  - 어떤 물건에서 난 소리인지
  - 어떤 소리 유형인지 (예: 탭, 구김, 긁힘, 찢김, 파손)
  - 어떤 재질인지 알고 있다면 재질
  - 강도·느낌·상황 등 추가 설명
  - 음원 출처 URL과 라이선스 정보 (알고 있는 경우)
- 설명이 정확하지 않아도 자연스럽게 적는다. 예: “택배 상자를 세게 눌렀을 때 나는 낮고 바스락거리는 소리 같아.”
- 우선 대상 물건인 책, 알루미늄 캔, 노트북 각각에 필요한 소리가 비어 있으면 Claude Code의 요청을 받아 해당 음원을 찾아 제공한다.

### Claude Code가 맡는 일

- 제공된 음원 파일이 실제로 존재하는지 확인하고 파일명을 안전하고 일관되게 정리한다.
- 자연어 설명에서 물건, 재질, 동작, 강도, 질감 태그를 추출한다.
- 설명에 없는 정보를 사실처럼 지어내지 않는다. 알 수 없으면 `unknown`으로 둔다.
- 카탈로그 데이터에 새 항목을 추가하거나 기존 항목을 갱신한다.
- 파일 정보, 출처·라이선스, 앱 사용 적합성을 기록한다.
- 음원 자체를 듣거나 분석할 수 없는 환경이면 실제 청취·음향 판정을 했다고 주장하지 않는다.
- 중복 파일을 임의 삭제하지 않는다. 중복 가능성만 표시한다.
- 음원 카탈로그와 우선 대상별 필요 소리 목록을 비교해 빠진 소리를 찾아 사용자에게 요청한다.
- 필요한 음원을 한 번에 알아보기 쉽게 묶어 요청하며, 사용자가 이미 제공했거나 대체 승인한 소리는 다시 요청하지 않는다.

## 3. 우선 대상 물건과 필요한 소리

초기 구현은 다음 세 물건을 우선한다. 소리는 앱의 가상 파손 연출에 사용한다. 실제 물건을 파손하라고 안내하거나 녹음을 요구하지 않는다. 안전한 소품을 사용한 녹음, 기존 효과음 라이브러리, 합성 음원을 사용할 수 있다.

| 물건 코드 | 물건 | 우선 재질 | 필요한 기본 소리 |
|---|---|---|---|
| `book` | 책 | 종이, 판지(표지) | 가벼운 탭, 강한 충격/눌림, 페이지·표면 마찰, 구김·압축, 파손 완료/책이 떨어지는 소리 |
| `aluminum_can` | 알루미늄 캔 | 알루미늄 | 가벼운 탭, 강한 타격, 눌러 찌그러뜨림, 긁힘·금속 떨림, 파손 완료/찌그러진 캔 굴림 |
| `laptop` | 노트북 | 알루미늄 또는 플라스틱 외장, 유리 화면, 내부 금속은 MVP에서 단순화 | 가벼운 탭, 강한 충격, 케이스 눌림·휘어짐, 표면 마찰, 파손 완료 효과음 |

### 최소 음원 준비 기준

각 물건마다 다음 4개 역할을 먼저 채운다. 한 파일이 여러 역할을 충족할 수 있지만, 실제로 들어 보거나 사용자가 설명한 근거가 있어야 한다.

1. `light_hit`: 가벼운 탭/충격
2. `strong_hit`: 강한 충격 또는 눌림
3. `scrape_or_rub`: 긁힘 또는 표면 마찰
4. `break_or_finish`: 파손 진행 완료를 표현하는 효과음

물건에 특화된 파일을 구하기 어렵다면 재질별 공용음을 후보로 사용할 수 있다. 예를 들어 책의 표지 소리는 판지 공용음을, 노트북 외장 충격은 알루미늄 또는 플라스틱 공용음을 사용할 수 있다. 이 경우 카탈로그에는 실제 녹음 물체와 앱에서 사용할 대상 물체를 구분해 적는다. 유리 파손처럼 해당 물건에 없는 부위를 임의로 노트북 파손음에 넣지 않는다.

Claude Code는 등록된 음원을 위 표와 대조해 각 물건·역할의 상태를 계산한다.

- `covered`: 사용 가능한 음원이 있음
- `missing`: 음원이 없음
- `needs_review`: 음원은 있으나 라이선스 미확인, 태그 불확실, 또는 적합성 확인이 필요함
- `covered_by_material_fallback`: 해당 물건 음원은 없지만 재질 공용음으로 대체 가능

## 4. 지원 재질

초기 카탈로그는 다음 8개 재질군을 기준으로 한다.

| 코드 | 표시명 | 예시 |
|---|---|---|
| `paper` | 종이 | 책 속지, 종이 한 장, 영수증 |
| `cardboard` | 판지·골판지 | 택배 상자, 종이 포장 상자 |
| `wood` | 목재 | 책상, 나무 상자, 연필 |
| `steel` | 철·강철 | 철제 프레임, 공구, 조리도구 |
| `aluminum` | 알루미늄 | 캔, 얇은 금속판, 일부 노트북 외장 |
| `glass` | 유리 | 컵, 병, 창문 |
| `ceramic` | 도자기·세라믹 | 머그컵, 접시, 타일 |
| `plastic` | 플라스틱 | 장난감, 케이스, 병 |

이 목록에 없는 재질은 새 코드로 임의 추가하지 말고 `other`로 기록하고 메모에 적는다. 이후 사용자가 재질군을 확장하기로 하면 별도 변경한다.

물건 하나가 여러 재질로 되어 있으면 재질을 여러 개 기록할 수 있다. 설명이 전체 물건 기준인지 특정 부위 기준인지 모르면 임의로 나누지 말고 메모하거나 `unknown`으로 처리한다.

## 5. 소리 유형 어휘

`action`에는 아래 코드 중 가장 알맞은 하나를 쓴다. 혼합 소리라면 하나를 대표 유형으로 고르고 나머지는 `secondary_actions`에 쓴다.

| 코드 | 의미 | 예 |
|---|---|---|
| `tap` | 가볍게 두드림 | 손가락으로 책상을 톡 침 |
| `impact` | 강한 충격·부딪힘 | 물체를 바닥에 떨어뜨림 |
| `press` | 누르거나 압축함 | 상자를 눌러 찌그러뜨림 |
| `crumple` | 구기거나 구겨짐 | 종이를 손으로 뭉침 |
| `scrape` | 긁거나 표면을 문지름 | 금속을 긁음 |
| `rub` | 마찰·비빔 | 천이나 종이를 문지름 |
| `tear` | 찢음 | 종이·천을 찢음 |
| `crack` | 금이 가거나 갈라짐 | 나무가 갈라지는 소리 |
| `break` | 파손·깨짐 완료 | 물건이 부서짐 |
| `rattle` | 흔들리며 부딪힘 | 금속 조각이 달그락거림 |
| `fall` | 떨어지거나 내려놓음 | 컵을 탁자에 내려놓음 |
| `other` | 위 유형으로 표현하기 어려움 | 설명을 메모에 보존 |

## 6. 강도와 질감 태그

### 강도 (`intensity`)

- `light`: 약한 소리·가벼운 동작
- `medium`: 보통 강도
- `strong`: 강한 동작·큰 충격
- `unknown`: 설명만으로 판단 불가

### 질감 (`texture_tags`)

다음 중 설명에 명시되거나 제공된 음원에서 실제 확인 가능한 것만 선택한다.

- `bright`: 밝고 고음 성분이 두드러짐
- `dull`: 둔탁하고 고음이 적음
- `resonant`: 울림이 비교적 길거나 분명함
- `dry`: 잔향이 짧고 가까운 소리
- `crunchy`: 바스락거리거나 부서지는 입자감
- `rattly`: 여러 작은 조각이 떨리거나 부딪힘
- `soft`: 부드럽고 완만함
- `sharp`: 짧고 날카로운 어택
- `low`: 낮은 주파수 성분이 두드러짐
- `unknown`: 확인할 근거가 없음

자연어 형용사를 그대로 메모에 보존할 수 있지만, 위 태그 중 근거 있는 것만 고른다. 자연어에서 “낮고 바스락거림”이라고 했다면 `dull` 또는 `low`와 `crunchy`를 후보로 기록하되 애매하면 `unknown`으로 둔다.

## 7. 사용자 입력 양식 (자연어로 작성 가능)

사용자는 정해진 양식을 꼭 지킬 필요가 없다. 아래는 편리한 예시다.

```text
파일: box_press_01.wav
설명: 택배 상자를 손으로 세게 눌렀을 때 나는 소리. 낮고 바스락거려.
출처: https://example.com/audio
라이선스: CC0
```

또는 자연어만 보내도 된다.

```text
이건 책장을 넘기는 소리야. 종이가 빠르게 스치는 느낌이고 아주 세진 않아. Freesound에서 받았어: (링크)
```

필수 최소 입력은 **음원 파일 또는 파일 경로 + 소리에 대한 자연어 설명**이다. 출처·라이선스를 모르면 추정하지 않는다.

## 8. Claude Code 처리 절차

음원과 설명을 받으면 다음 순서로 처리한다.

1. **파일 확인**
   - 지정된 파일이 실제 경로에 있는지 확인한다.
   - 접근할 수 없는 파일을 받은 것처럼 기록하지 않는다.
   - 지원 가능한 경우 확장자, 파일 크기, 재생 시간, 샘플레이트, 채널 수를 읽는다.
   - 음원을 직접 청취·파형 분석하지 못한 경우 이 사실을 기록한다.

2. **파일 ID 생성**
   - 형식: `{material}_{action}_{NNN}`
   - 예: `cardboard_press_001`, `paper_turn_002`
   - 같은 ID가 있으면 다음 번호를 사용한다.
   - 원본 파일명은 메타데이터의 `original_filename`에 보존한다.

3. **자연어 태깅**
   - 물건, 재질, 동작, 강도, 질감을 구조화한다.
   - 확신이 없는 값은 `unknown`으로 둔다.
   - 사용자 설명에서 추론한 내용과 청취·분석으로 확인한 내용을 구분한다.

4. **라이선스 기록**
   - URL, 라이선스명, 저작자, 출처 표기 필요 여부를 제공된 정보만 기록한다.
   - 라이선스가 확인되지 않으면 `unverified`로 표시하고 앱 배포 가능 상태를 `review_required`로 설정한다.
   - 라이선스가 `NC`이거나 게임·앱 내 배포를 허용하는지 모호하면 상업 앱 사용 가능으로 표시하지 않는다.

5. **카탈로그 갱신**
   - 아래 스키마에 맞춰 `sounds/catalog.json`을 갱신한다.
   - 사람이 읽을 수 있는 표 형식 카탈로그 `sounds/README.md`도 함께 갱신한다.
   - 프로젝트에 이미 다른 파일 구조가 있으면 기존 구조를 먼저 확인하고 불필요한 파일을 새로 만들지 않는다.

6. **검증**
   - JSON 파싱이 되는지 확인한다.
   - 모든 `file_path` 값이 실제 파일을 가리키는지 확인한다.
   - `sound_id` 중복 여부를 확인한다.
   - 라이선스 확인이 필요한 항목을 결과에 요약한다.

7. **결과 보고**
   - 추가한 음원 ID, 추출한 태그, 확인되지 않은 정보, 수정된 파일을 간단히 알린다.
   - 중요한 정보가 누락되면 추측해 채우지 말고 `unknown` 또는 `review_required`로 둔다.

8. **필요 음원 점검 및 사용자 요청**
   - `sounds/catalog.json`을 우선 대상 물건별 필요 소리 표와 대조한다.
   - `app_use_status`가 `approved`인 음원만 `covered`로 센다. 라이선스 미확인 음원은 `needs_review`로 센다.
   - 직접 음원이 없지만 승인된 재질 공용음이 적절하면 `covered_by_material_fallback`으로 표시한다.
   - 누락 항목을 물건별로 묶어 사용자에게 요청한다. 파일을 이미 전달받은 항목, 이전에 대체 승인한 항목은 다시 묻지 않는다.
   - 모든 필수 항목이 채워지면 추가 음원을 요청하지 않고 준비 상태를 보고한다.
   - 사용자가 즉시 음원을 제공하지 않아도 진행을 막지 않는다. 카탈로그에 `missing`을 남기고 다음 작업으로 이어간다.

### 사용자에게 보내는 음원 요청 형식

누락된 소리가 있을 때 다음처럼 간결하게 요청한다.

```text
아직 필요한 음원:
- 책: 페이지/표면 마찰, 파손 완료음
- 알루미늄 캔: 눌러 찌그러뜨리는 소리, 금속 떨림
- 노트북: 케이스 충격, 표면 마찰

각 소리는 파일과 함께 자연어 설명을 보내주세요. 예: “빈 알루미늄 캔을 손으로 눌러 찌그러뜨리는 짧고 얇은 소리.”
출처 링크와 라이선스를 알면 같이 적어주세요. 모르면 미확인이라고 표시해도 됩니다.
물건 전용 녹음이 없으면 해당 재질의 공용 효과음도 받을 수 있습니다.
```

실제 요청에는 위 예시 전체가 아니라, 카탈로그에서 그 시점에 확인된 `missing` 및 필요 시 `needs_review` 항목만 넣는다.

## 9. 카탈로그 데이터 스키마

`sounds/catalog.json`에 다음 구조로 저장한다.

```json
{
  "schema_version": 1,
  "sounds": [
    {
      "sound_id": "cardboard_press_001",
      "file_path": "assets/audio/cardboard/cardboard_press_001.wav",
      "original_filename": "box_press_01.wav",
      "object_names": ["택배 상자", "상자"],
      "target_objects": ["book", "aluminum_can", "laptop"],
      "material_codes": ["cardboard"],
      "action": "press",
      "secondary_actions": ["crumple"],
      "intensity": "strong",
      "texture_tags": ["low", "crunchy"],
      "description_original": "택배 상자를 손으로 세게 눌렀을 때 나는 낮고 바스락거리는 소리.",
      "source_url": "https://example.com/audio",
      "source_name": "Example Audio Library",
      "creator": "unknown",
      "license": "CC0",
      "attribution_required": false,
      "license_status": "verified_from_user_input",
      "app_use_status": "review_required",
      "duration_seconds": null,
      "sample_rate_hz": null,
      "channels": null,
      "tagging_basis": "user_description",
      "confidence": "medium",
      "notes": "실제 청취 분석은 수행하지 않음.",
      "added_at": "YYYY-MM-DD"
    }
  ]
}
```

### 필드 규칙

- `sound_id`: 고유한 snake_case ID.
- `file_path`: 프로젝트 루트 기준 상대 경로.
- `original_filename`: 사용자가 준 원본 이름.
- `object_names`: 사용자가 언급한 실제 물건 이름. 모르면 빈 배열.
- `target_objects`: 앱에서 이 음원을 적용해 볼 수 있는 대상 코드. 실제 녹음 물건이 아니라 앱 내 후보 연결이며, 사용자 설명이나 승인된 재질 폴백으로 뒷받침되는 대상만 쓴다. 모르면 빈 배열.
- `material_codes`: 위 8개 코드 중 하나 이상. 모르면 `["unknown"]`.
- `action`: 대표 소리 유형 코드 하나.
- `secondary_actions`: 추가로 명확한 동작이 있을 때만 입력.
- `intensity`: `light`, `medium`, `strong`, `unknown` 중 하나.
- `texture_tags`: 허용된 질감 코드만 사용.
- `description_original`: 사용자 설명 원문을 가능한 한 보존.
- `source_url`, `source_name`, `creator`: 확인되지 않으면 `unknown` 또는 `null`.
- `license`: 라이선스 표기 원문. 모르면 `unknown`.
- `attribution_required`: 명확히 확인되지 않으면 `null`.
- `license_status`: `verified_from_user_input`, `verified_from_source_page`, `unverified` 중 하나.
- `app_use_status`: `approved`, `review_required`, `not_approved` 중 하나. 확인 전 기본은 `review_required`.
- `duration_seconds`, `sample_rate_hz`, `channels`: 파일에서 읽을 수 있으면 기록하고 아니면 `null`.
- `tagging_basis`: `user_description`, `listening`, `metadata`, `mixed` 중 하나.
- `confidence`: `high`, `medium`, `low` 중 하나. 파일에 접근 못하면 `low`.
- `added_at`: 실제 등록 날짜. 날짜를 모르면 작성일 기준으로 입력.

## 10. 디렉터리 구조 권장안

프로젝트에 이미 정해진 구조가 없다면 아래를 사용한다.

```text
sounds/
  catalog.json
  README.md
assets/
  audio/
    paper/
    cardboard/
    wood/
    steel/
    aluminum/
    glass/
    ceramic/
    plastic/
    unclassified/
```

원본 파일을 변환해야 하면 원본을 보존하고 앱용 변환본을 별도로 만든다. 원본을 덮어쓰지 않는다. 변환 프로그램이나 명령을 실행하기 전에는 프로젝트의 기존 도구와 지침을 확인한다.

## 11. 소리 조합을 위한 후속 규칙

앱은 초기에는 아래 특성으로 음원을 검색해 조합한다.

1. 물건 이름이 맞는 음원을 우선한다.
2. 물건 음원이 없으면 재질과 동작이 일치하는 음원을 찾는다.
3. 정확히 일치하는 항목이 없으면 같은 재질의 유사 동작을 후보로 제시한다.
4. 재질이 여러 개인 물건은 해당 부위의 재질 태그가 일치하는 소리를 사용한다.
5. 라이선스 상태가 `review_required` 또는 `not_approved`인 음원은 출시 빌드에 포함하지 않는다.
6. 후보가 여럿이면 동작, 강도, 질감의 일치도를 기준으로 정렬한다.
7. 적합한 음원이 없으면 엉뚱한 재질을 자동 선택하지 말고 일반 효과음 폴백을 사용한다.

초기에는 이 검색·정렬을 규칙으로 구현한다. 카탈로그 항목만으로 머신러닝 모델을 학습시켰다고 표현하지 않는다. 별도 학습이 필요해지면 충분한 사용자 평가 데이터, 학습·검증 분리, 데이터 사용 권리 확인을 추가한다.

## 12. 라이선스와 출처 관리

- 각 음원 파일과 카탈로그 항목은 출처 URL과 라이선스에 연결되어야 한다.
- “무료”, “로열티 프리”라는 설명만으로 앱 내 상업적 사용이 허용된다고 판단하지 않는다.
- 편집·변형 허용, 앱에 내장해 배포할 수 있는지, 출처 표시 의무를 확인한다.
- 확인할 수 없는 음원은 `review_required`로 남긴다.
- 필요한 출처 표기는 앱의 크레딧 화면 또는 프로젝트의 `sounds/attributions.md`에 정리한다.

## 13. Claude Code 작업 지시 템플릿

음원 파일과 자연어 설명을 전달할 때 아래 지시를 사용할 수 있다.

```text
이 음원과 설명을 프로젝트의 음원 카탈로그에 등록해줘.

설명: [자연어 설명]
출처/라이선스: [알고 있는 내용 또는 미확인]

이 문서의 규칙에 따라 파일 존재 여부와 메타데이터를 확인하고,
파일명을 정리한 뒤 sounds/catalog.json과 sounds/README.md를 갱신해줘.
모르는 정보는 추측하지 말고 unknown 또는 review_required로 표시해.
원본 음원을 덮어쓰거나 삭제하지 말고, 마지막에 추가한 ID와 미확인 항목을 요약해줘.
```

## 14. 음원 요청과 준비 현황 확인 템플릿

사용자가 “필요한 소리 알려줘”, “뭐가 부족해?”라고 요청하면 다음 작업을 한다.

1. 기존 카탈로그를 읽고 책·알루미늄 캔·노트북의 네 가지 필수 역할별 상태를 확인한다.
2. 물건별로 `missing`인 역할을 나열한다.
3. 승인된 재질 공용음으로 대체할 수 있는 경우 대체 후보와 재질을 함께 표시한다.
4. `needs_review` 항목은 누락과 구분해 라이선스 또는 태그 확인이 필요하다고 알린다.
5. 자연어 설명과 파일을 보내는 방법을 안내한다. 필요한 음원이 없으면 계속 진행할 수 있다고 알린다.

음원 요청 결과는 아래처럼 요약한다.

```text
음원 준비 현황
- 책: 가벼운 충격 있음, 강한 충격 있음, 마찰 부족, 완료음 부족
- 알루미늄 캔: 재질 공용음으로 충격 대체 가능, 찌그러짐 있음, 완료음 검토 필요
- 노트북: 충격 부족, 마찰 부족, 나머지 재질 공용음 후보 있음

이번에 보내주면 좋은 소리:
1. 책 표면을 넘기거나 문지르는 소리
2. 책이 닫히거나 떨어질 때의 완료 효과음
...
```

## 15. 수용 기준

음원 등록 작업은 다음을 만족하면 완료다.

- 카탈로그가 JSON으로 정상 파싱된다.
- 파일 경로가 실제 제공된 음원 파일과 일치한다.
- 물건, 재질, 동작 태그가 자연어 설명과 모순되지 않는다.
- 불확실한 정보가 추측으로 채워지지 않았다.
- 출처와 라이선스가 기록되며, 미확인 음원은 검토 대상으로 표시된다.
- 카탈로그 표에도 같은 항목이 반영된다.
- 기존 음원과 파일을 삭제하거나 덮어쓰지 않았다.
- 책, 알루미늄 캔, 노트북 각각의 필요 소리 현황을 갱신했다.
- 부족한 음원이 있으면 물건과 소리 역할을 구체적으로 묶어 사용자에게 요청했다.
